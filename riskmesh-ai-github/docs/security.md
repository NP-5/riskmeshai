# Security notes
- **Authentication:** static bearer tokens (`token:identity:role`, ≥16 chars) compared in constant time against all tokens. Static tokens are a hackathon-grade choice; use SSO/OIDC in front for real deployments. Tokens are held in `sessionStorage` by the dashboard (cleared with the tab).
- **Authorization:** roles enforced in the service layer as well as the router. Only `reviewer`/`admin` approve; the agent and MCP server cannot.
- **Money movement:** one write action (cancel unclaimed payout item). Conditional state changes + partial unique index prevent double execution (tested with 6 concurrent approvals). The cancel call is never retried; outcome is verified by reading the item back.
- **Webhook trust:** only PayPal's verify API can mark an event verified; certificate URLs must be HTTPS `*.paypal.com`; no verification configured ⇒ 503 (fail closed). Demo mode is separate, labelled `DEMO_UNVERIFIED`, and refused in production.
- **Data handling:** recipient identifiers are peppered SHA-256 hashes plus a masked display; logs/audit are redacted for credentials and email addresses. The raw webhook payload is stored for audit in `webhook_events.payload_json` and **can contain personal data** (e.g. a payout receiver email): restrict database access and set a retention policy; no API returns it.
- **Prompt injection:** record text never feeds the decision; model output is limited to reviewer-verified inferences; tested with injected memo/custom-id text.
- **Known gaps:** rate limiting is in-memory per process; no CSRF concern (bearer header, no cookies) but no token rotation/expiry; SQLite WAL on a single node is not HA; PostgreSQL path untested; no dependency scanning performed; not penetration tested.

- **Data sent to Gemini (when enabled):** capture/payout amounts, statuses, timestamps, dispute reasons, hashed recipient ids and claim text. Device, IP and payer ids are replaced by per-request random tokens. Review Google's Gemini API data-use terms for your key type (free-tier prompts may be used to improve products) before sending anything real; with synthetic or sandbox data this is low risk. The key is read from the environment, sent only in a header, never logged, never returned by any endpoint and never put in an error message (tested).
